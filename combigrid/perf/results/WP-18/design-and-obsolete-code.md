# WP-18 — design notes, lazy vs. eager, obsolete code

## Storage (decisions taken in this WP)

- **Where**: `SparseGridBase` (both grid types): `LvlMIVec levels_` (moved in from the MI-set
  generation; owned, so it never aliases the caller's `LvlMIVec` of an `MIVecSGGenInstr`),
  `std::vector<CTCoeffType> coefficients_`, `NodeTable nodeTable_` (domain), `NodeTable
  unitNodeTable_` (unit interval; owner's choice 2026-11-14, see below), cached maxima,
  `OperatorDataCache` (moved up from `DeltasSparseGrid`).
- **Index**: row = `firstRowOfDim[dim] + lvl` (level-indexed, levels 0 … maxLvl(dim)). The number of
  grid points per dimension is the row length (no per-TG counts stored). SG rows: regular nodes
  (with boundary iff lvl ≥ offset); DSG rows: delta nodes (boundary at lvl == offset) — for nested
  nodes the rows of one dimension are exactly the nodes of its finest level, each once.
- **Identical lists of different dimensions**: shared → `sharesRowsWith`. Unit table: same
  `NodeGenFunc*` and `Lvl2GPCntFunc`; domain table: also the same domain interval. Cheap (one scan
  at generation), saves half of each table at d2. Rows of a group are generated from the group's
  dimension with the highest level (the first one may have fewer levels).
- **Nested-node dedup across levels (SG)**: not done. The SG table holds ≈ 2× the finest level per
  dimension; a strided view into the finest level would only work for families whose level-l nodes
  are an equal-stride subset (equi / CC with doubling), adds stride arithmetic to the hot loops and
  is not generic. The table is no longer a memory driver (d2 L20: 32 MiB).
- **Rows as separate `DataVector`s** (not one flat buffer): each row is allocated, zero-filled and
  generated by the thread that generates it (a flat buffer was zero-filled serially:
  d2 L20 shifted domain, 16 threads 27 → 81 ms; per-row storage 22 ms).
- **Two tables, both eager** (owner's choice 2026-11-14, option 1 of: both eager / unit lazy as
  operator data / unit only + domain mapped on the fly): weights, basis values and interpolation
  cells are computed on [0,1]^d from `getUnitNodeTable()` (bitwise identical results and corners as
  before); the source function is evaluated at `getDomainNodeTable()` nodes. The unit table is generated
  (node-generation functions), the domain table is its `mapToDomain` copy (no second node
  generation). Users: SG global interp (basis values), SG linear interp (bracket), DSG linear-interp
  index (sorted copies of the unit delta rows instead of regenerating them). Computing in domain
  coordinates instead changed which corner is selected for query points exactly on nodes of
  shifted domains (normalization rounds the point off the node) — kept out. Replaces the lazily
  built `misc::UnitNodeTable` operator data of the first variant (snapshot `WP-18-lazyunit`).
- **Accessors** (owner's choice 2026-11-15): every tensor-grid accessor names its coordinates
  (`getDomainTensorGrid` / `getUnitTensorGrid`, `domainTensorGrids()` / `unitTensorGrids()`,
  `getDomainNodeTable` / `getUnitNodeTable`); no default iteration (a class can have only one
  `begin`/`end`). Both variants are the same view type, only the table pointer differs: no cost.
  Rejected: a coordinate parameter (range-for cannot take one; runtime choice in the loops) and
  both views in `TensorGridCTDataView` (+32 bytes per view and dereference, also for the
  quadrature). Risk: unit and domain views have the same type (mix-ups compile); kernels name
  their parameters `tg` / `unitTG`, tests check the coordinates of both variants.
- **Not unit-table users**: `DSGGlobalInterpIndex` needs the regular SG nodes of every level (not
  the delta nodes the DSG tables hold) and still generates them; the quadrature weights depend
  only on the node count.
- **Views**: `TensorGridView` caches raw pointers to the table's rows (2 dependent loads per node
  list instead of 4); passed by const reference in the linear-interpolation kernel (by value it
  forced a 32-byte aligned stack copy per call: 1-thread `interplin/sg` d2 L12 4.39 → 3.72 µs).

## Lazy vs. eager node tables (owner's suggestion, evaluated, eager kept)

Measured (`lazy-vs-eager.txt`, 16 threads, median of 11). First variant (one domain table generated
directly):

| grid | construction | MI set + coefficients | node table (nodes, size) |
|---|---|---|---|
| sg cc b0 d2 L20 | 51.6 ms | 0.01 ms | 50.5 ms (4.19 M, 32 MiB) |
| sg equi b0 d2 L20 | 16.7 ms | 0.01 ms | 9.3 ms (4.19 M, 32 MiB) |
| sg cc b1 d20 L5 | 9.3 ms | 8.8 ms | 0.009 ms (130) |
| dsg equi b1 d20 L6 | 3.6 ms | 1.8 ms | 0.005 ms (129) |

Final variant (unit table generated + domain table mapped from it):

| grid | construction | unit table | domain table (nodes, size of both) |
|---|---|---|---|
| sg cc b0 d2 L20 | 64.1 ms | 41.4 ms | 8.5 ms (2 × 4.19 M, 64 MiB) |
| sg equi b0 d2 L20 | 27.7 ms | 6.7 ms | 7.9 ms (2 × 4.19 M, 64 MiB) |
| sg cc b1 d20 L5 | 9.2 ms | 0.009 ms | 0.007 ms |
| dsg equi b1 d20 L6 | 3.5 ms | 0.007 ms | 0.007 ms |

| | eager (implemented) | lazy (first node-reading operator) |
|---|---|---|
| generation time | includes the tables: negligible in high d, the whole cost of deep low-d grids (d2 L20: 28–64 ms) | MI set + coefficients only |
| first operator call | unchanged | + the same table build (every operator reads nodes), so the pipeline time is unchanged |
| peak memory | tables ≤ 64 MiB (d2 L20), < 6 KiB in high d | identical once any operator ran |
| code | none | thread-safe publication on a `const` grid (`call_once` / atomic pointer) in every accessor |

Recommendation: eager (both tables). e2e of the eager unit table vs. the lazy operator-data unit
table of the first variant (`e2e-unit-table.md`): totals within noise, generation +12–20 ms at
d2 L20 (the quadrature never needed the unit table), peak memory geomean 0.994.

## Weights (for WP-05)

A per-call 1D weight table should use the `NodeTable` row index as key: weights depend on
(node family, count) only, i.e. on the row — and rows shared between dimensions get shared weights
automatically. Rows of different dimensions with equal family/count but different domain intervals
are separate rows; a WP-05 table keyed by (`QuadRule*`, nNodes) would merge those too. The SG
kernel then reads `weights + rowStart[row(dim, lvl)]` like the nodes (no `weights1D` scratch copy,
which is the remaining 268 MiB zero fill at sg d2 L20).

## Future dimension-adaptive CT

- Helpful: levels in an `LvlMIVec` (append / lookup / component-wise max cached), coefficients in
  one array (re-computing them after an MI insertion only rewrites the array), node rows indexed by
  (dim, lvl): adding a TG adds at most one row per dimension (`maxLvl` + 1) and never touches
  existing rows (rows are separate `DataVector`s: appending a row does not move the others, views
  of other rows stay valid). Function values can be keyed per grid point by (TG levels, node
  indices) or by the domain coordinates, which are bitwise the table's nodes.
- Blocking / to do then: `setStorage` replaces everything (an incremental `addTensorGrids` +
  `NodeTable::extend(dim, newMaxLvl)` is needed); views hold raw pointers into `rows_` (a
  `std::vector<DataVector>`): growing the row vector invalidates live views (reserve, or use
  `std::deque`-like stable storage); the DSG `OperatorDataCache` entries (tries, indices) would need
  invalidation on growth. Per-TG contributions are already available from the SG kernels
  (`processTensorGrid`); the DSG quadrature does not form them (needs the SG operator or a per-TG
  accumulation).
